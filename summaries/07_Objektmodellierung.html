Wichtig: Das Analysemodell (Objektmodellierung dieser Vorlesung) beschreibt ausschließlich Problembereichsklassen — es ist explizit kein Lösungsentwurf ("It is not meant to be a solution design!").

Object vs. Class

Object (Exemplar/Instance): genau ein konkretes Ding.
Class: beschreibt abstrakt eine Kategorie von Objekten mit ähnlichen Eigenschaften.
  • Klassendiagramm: beschreibt alle möglichen Zustände der Daten (Spezifikation).
  • Objektdiagramm (Instance Diagram): ein konkretes Set von Objekten/Beziehungen für ein Beispiel, Szenario oder einen Testfall (Illustration).

Objektarten (Entity / Control / Boundary)

ArtRepräsentiertÄnderungshäufigkeit
Entity Objectspersistente, vom System verfolgte Information ("business objects", "Geschäftsobjekte")am niedrigsten
Control Objectsdie vom System durchgeführten Steuerungsaufgaben ("Logik")mittel
Boundary Objectsdie Interaktion zwischen Benutzer und Systemam höchsten

Diese Dreiteilung macht Modelle änderungsresistenter. Oft "Model, View, Controller" (MVC) genannt — dieser Begriff passt aber eigentlich nur innerhalb von GUIs (also für Lösungsklassen). In UML als Stereotyp notierbar («Entity», «Control», «Boundary») oder per Namenskonvention (Suffix _Control, _Boundary).

Wie findet man Klassen? Abbotts Textanalyse

Methoden (mehrere kombinieren): Kunden beobachten/befragen, Weltwissen & Intuition nutzen, syntaktische Analyse von Anforderungstexten/Szenarien (Abbott 1983, "noun-verb analysis").

Ablauf des Object Modeling

  1. Szenarien formulieren (mit Endnutzer/Domänenexpert·in)
  2. Use Cases aus den Szenarien extrahieren
  3. Flow of Events analysieren (z. B. mit Abbotts Textanalyse)
  4. Klassendiagramm erzeugen: Klassen → Attribute/Operationen → Assoziationen → Multiplizitäten → Rollen

Reihenfolge ist nur eine Heuristik, flexibel; Iteration hilft. Werden falsche Abstraktionen gefunden, müssen Inkonsistenzen erkannt und das Modell korrigiert werden.

Checklisten

  • Klassen: Kategorie identifizieren (Personen/Rollen, Orte, Ereignisse, Verträge, Handlungsinformationen, Container, konkrete Dinge); passenden Namen finden (Nutzerbegriff, Singular-Nomen); Abstraktionsniveau prüfen; wirklich eine Problembereichsklasse (nicht versehentlich eine Lösungsklasse, z. B. ein technischer Container)?
  • Assoziationen: erst einfache Linie; Art prüfen (physischer/logischer Teil von, Beschreibung von, nutzt, besitzt, andere); Restriktionen ({ordered}, {xor}, {subset}); Rollen benennen; reflexive Assoziationen immer benennen; 1:1-Assoziationen hinterfragen (sollten die Klassen vereint werden?); mehrere Assoziationen zwischen denselben Klassen wirklich unterschiedlich?
  • Attribute: Abstraktionsniveau prüfen (komplexe Attribute lieber als eigene Klasse, keine Implementierungsdetails modellieren); Lage prüfen (wäre das Attribut auch ohne die Assoziation nötig? Wenn nein: evtl. Attribut der Assoziation/Assoziationsklasse); passender Name (Nomen oder Adjektiv+Nomen, nicht Klassenname wiederholen).
  • Inheritance: natürlich (spiegelt eine echte Taxonomie der Problemdomäne)? redundant (zwei Unterklassen brauchen dieselben Attribute/Operationen)? fehlausgerichtet (Unterklasse erbt unpassende Operationen — sehr gefährlich)? Hinweis: Vererbung im Analysemodell muss im Entwurf/Code nicht zwingend als Vererbung realisiert werden.
  • Operationen: richtige Klasse (in Hierarchien so weit wie sinnvoll nach oben verschieben)? passender Name (Prozeduren: Imperativ, beschreibt Effekt; Funktionen: Nomen, beschreibt Rückgabe)? Kohäsion prüfen (Attribute ohne zugehörige Operation → fehlende Operation); zu viele Parameter → Hilfsklasse einführen.

Praktische Hinweise für Diagramme

  • Ravioli-Modelle vermeiden: nicht zu viele Klassen in ein Diagramm packen — Faustregel 5 bis 10 Klassen.
  • Taxonomien (Vererbungshierarchien) auf ein separates Diagramm auslagern.
  • Explizite Meetings für Objektidentifikation einplanen: erst Objekte finden → dann in Entity/Boundary/Control differenzieren → Assoziationen+Multiplizität finden (am besten von konkreten Instanzdiagrammen ausgehend) → Vererbung identifizieren → Aggregation identifizieren → wichtige Methoden/Attribute identifizieren. Immer wieder iterieren.

Wer nutzt Klassendiagramme? Analyst- vs. Designer- vs. Implementor-Sicht

Kurzformel dazu (uebersicht.txt Zeile 256): Analysten sind an der Struktur interessiert, Entwerfer sind an der Lösung interessiert — Analysten modellieren, welche Konzepte/Taxonomien in der Anwendungsdomäne existieren; Entwerfer nehmen diese Struktur als gegeben und suchen dazu passende Lösungsklassen/Schnittstellen.

  • Kund·innen/Endnutzer·innen interessieren sich kaum dafür (die interessiert eher Verhalten → Use Cases).
  • Domänenexpert·innen (Analyst): nutzen Klassendiagramme zur Modellierung der Anwendungsdomäne → Analysemodell. Interessiert an Problembereichsklassen und daran, ob Vererbung die Taxonomien der Anwendungsdomäne widerspiegelt. Nicht interessiert an Lösungsklassen oder exakten Operationssignaturen.
  • Entwickler·innen (Designer): nutzen Klassendiagramme in Analyse, System-Entwurf, Objekt-Entwurf und Implementierung → Entwurfsmodelle. Entwurfsmodelle erweitern und verändern das Analysemodell — man darf das Analysemodell nie einfach als Entwurfsmodell annehmen! Designer fokussieren auf die Lösungsdomäne, betrachten Problembereichsklassen als weitgehend gegeben, suchen passende Lösungsklassen. Zentrales Entwurfsproblem: Spezifikation geeigneter Schnittstellen (erst der Subsysteme = Architekturentwurf, dann der Klassen), sodass alle funktionalen und nichtfunktionalen Anforderungen erfüllbar sind und der Entwurf leicht zu implementieren/testen/verstehen/ändern ist.
  • Implementor·innen — drei Rollen: Class implementor (implementiert die Klasse, wählt Datentypen/Algorithmen, realisiert die Schnittstelle in einer Programmiersprache), Class extender (entwirft eine Unterklasse, muss ggf. Teile der Oberklassenimplementierung verstehen), Class-user/Client (will eine bestehende Klasse nutzen, interessiert nur an der Schnittstelle: Signaturen, Vor-/Nachbedingungen — sollte die Implementierung nicht kennen müssen).

Zusammenfassung

Das Analysemodell spiegelt Konzepte aus Anwendungsdomäne und Anforderungen wider und wird durch systematische Analyse von Use Cases (plus weitere Techniken) gefunden. Das darauffolgende Entwurfsmodell ist meist deutlich anders: Es lässt oft etliche Problembereichsklassen weg (weil für das technische System nicht relevant) und enthält üblicherweise viele zusätzliche Lösungsklassen.
