  • multireceive (Objektfluss-Stereotyp): das Gegenstück — mehrere eingehende Objektflüsse werden an einem Knoten wieder zusammengeführt/gesammelt (z. B. wenn mehrere Akteure unabhängig voneinander Ergebnisse an eine Stelle zurückmelden).

Dynamic Model — Grundlagen

Ein dynamisches Modell ist eine Sammlung mehrerer Verhaltensdiagramme (State-Machine-, Aktivitäts-, Sequenzdiagramme) — meist mindestens eines pro wichtiger Klasse mit relevantem dynamischen Verhalten.
  • Zweck: Verhaltensanforderungen verstehen; fehlende Methoden fürs Objektmodell aufdecken und liefern.
  • Vorgehen: von Use Case/Szenario + identifizierten Klassen ausgehen → Interaktion zwischen Objekten modellieren (Sequenzdiagramm) bzw. Verhalten eines einzelnen Objekts modellieren (State-Machine-Diagramm).

Sequenzdiagramme zur Objektmodellierung nutzen

Notation selbst siehe 04 UML; hier geht es um den Einsatz beim Entdecken von Klassen/Operationen

  • Typisches Layout: 1. Spalte der auslösende Akteur, 2. Spalte ein Boundary-Objekt (im Entwurf, in der Analyse evtl. nicht), 3. Spalte evtl. ein Control-Objekt, das den Use Case steuert, weitere Spalten die übrigen beteiligten Objekte.
  • Erzeugung: Control-Objekte werden oft bei Beginn eines Use Case erzeugt; weitere Boundary-Objekte können von Control-Objekten erzeugt werden.
  • Zugriff: Entity-Objekte werden von Control- und Boundary-Objekten angesprochen; Entity-Objekte sollten nie Boundary- oder Control-Objekte aufrufen.
  • Für jedes Objekt, das eine Nachricht (Event) empfängt, entsteht eine öffentliche Operation in der zugehörigen Klasse (Name der Operation meist = Name des Events).

Fork- vs. Stair-Diagramme (Jacobson) — eine Entwurfs-, keine Analysefrage!

StilStrukturVorteil
Fork (zentrale Kontrolle)viel Verhalten steckt in einem einzigen (meist Control-)Objekt, das alle anderen kennt und direkt befragt/befehligtunterstützt Änderungen besser: Reihenfolge leicht änderbar, neue Operationen leicht einfügbar
Stair (dezentrale Kontrolle)Verhalten verteilt: jedes Objekt kennt nur wenige andere und delegiertlokal einfach: Objekte bleiben überschaubar, Verantwortlichkeiten leicht verständlich

Kein Stil ist grundsätzlich besser — meist ist eine geeignete Mischung sinnvoll (siehe Entwurfsmuster "Mediator", "Fassade").

Zustandsdiagramme (State Machine Diagrams)

Ein Zustandsautomat beschreibt den Lebenszyklus eines Objekts: ein Graph, dessen Knoten Zustände und dessen gerichtete Kanten (Transitions) mit Ereignisnamen beschriftete Übergänge sind. Ein Zustandsdiagramm bezieht sich immer auf eine Klasse (ein Objektmodell mit mehreren Klassen kann entsprechend mehrere Zustandsdiagramme haben).

Übung 6-3a: Aktionen an Transitions vs. in States — Notation und Semantik

Notation:
  • An einer Transition (Pfeil zwischen zwei Zuständen): Event(Parameter) [Guard-Bedingung] / Aktion — steht direkt auf dem Pfeil.
  • In einem Zustand (im Zustandskästchen selbst): entry/Aktion, exit/Aktion, do/Aktivität, oder event/Aktion als eigene Zeilen im Zustandskörper.
Semantischer Unterschied:
  • Transition-Aktion: wird genau einmal ausgeführt, während des Übergangs von einem Zustand in einen anderen (der Zustand wechselt).
  • entry-Aktion: wird einmal ausgeführt, sobald der Zustand betreten wird (unabhängig davon, über welche Transition).
  • exit-Aktion: wird einmal ausgeführt, sobald der Zustand verlassen wird.
  • do-Aktivität: läuft, solange sich das Objekt in diesem Zustand befindet (kontinuierlich/wiederholt), bis der Zustand verlassen wird.
  • event/Aktion im Zustand: ein interner Übergang — das Ereignis wird behandelt, ohne den Zustand zu verlassen (kein Entry/Exit wird ausgelöst).

Präzisierung aus other/statecharts_activitydiagrams.pdf:

  • Interne Transition (Event als Zeile im Zustandskästchen): Ein- und Austrittsverhalten (entry/exit) werden nicht ausgelöst — der Zustand wird ja nicht verlassen.
  • Selbsttransition (ein Pfeil vom Zustand zurück zu sich selbst): Ein- und Austrittsverhalten werden wohl ausgelöst — der Zustand wird formal verlassen und sofort wieder betreten.
Praxistipp aus der Folie: Notationsclutter reduzieren, indem man Aktionen möglichst in die Zustandskästchen legt (v. a. wenn identische Aktionen bei Events auf denselben Zielzustand vorkommen).

Was ist ein "Zustand"?

  • Eine Abstraktion der Attributwerte eines (späteren) Implementierungsobjekts: eine "passende" Äquivalenzklasse von Attributwert-Konfigurationen, die nicht weiter unterschieden werden müssen (was "passend" ist, hängt vom aktuellen Ziel ab).
  • Ein Zustand hat eine Dauer. Manche Zustände brauchen keinen (oder keinen aussagekräftigen) Namen, aber trotzdem weitere Details (z. B. entry-Aktion).

Aktivität vs. Aktion (innerhalb eines Zustandsautomaten)

  • Activity: zusammengesetzte Operation — kann durch ein eigenes Aktivitätsdiagramm weiter beschrieben werden.
  • Action: elementare Operation (kann intern zwar auch Struktur haben, wird vom Zustandsautomaten aber ignoriert).

Verschachtelte/zusammengesetzte Zustände (Composite States)

  • Ein Zustand kann selbst wieder als eigener kleiner Zustandsautomat (Unterzustände mit eigenem Start-/Endpunkt) ausmodelliert werden — im übergeordneten Diagramm nur als ein Zustand mit kleinem Doppelkreis-Symbol angedeutet.

Nebenläufigkeit (Concurrency)

ArtBedeutung
System Concurrency (zwischen Objekten)Zustand des Gesamtsystems = Aggregation der Zustandsautomaten aller Objekte; jeder Zustandsautomat läuft konzeptuell nebenläufig zu allen anderen. Ein Zustandsdiagramm (pro Klasse) kann zu vielen Zustandsautomaten führen (einer pro Instanz).
Object Concurrency (innerhalb eines Objekts)ein Objekt wird in mehrere parallele Zustands-Teilbereiche ("Regions", getrennt durch gestrichelte Linien) aufgeteilt; der Gesamtzustand besteht aus je einem Zustand pro Region. Split/Synchronisation werden durch Balken (fork/join) notiert.

Nebenläufigkeit wird in diesem Kurs meist weitgehend ausgeklammert.

Praktische Tipps für State-Machine-Modellierung

  1. Nur für Klassen mit signifikantem/komplexem dynamischen Verhalten modellieren (sonst "Analysis Paralysis") — Ausnahme: wenn Zustandsdiagramme direkt zur Codegenerierung ausreichen (z. B. Steuerlogik in Telekommunikationssystemen).
  2. Nur relevante Attribute bei der Zustandsdefinition berücksichtigen — Abstraktion konsequent nutzen.
  3. Sinnvolle Granularität von Aktionen/Aktivitäten wählen — das ist immer noch Analyse, kein Entwurf!
  4. Notationsclutter reduzieren (Aktionen wenn möglich in Zustandskästchen statt an jeder Transition).

Dynamische Modellierung von Benutzeroberflächen

Zustandsdiagramme eignen sich auch, um Navigationspfade/Page-Flows einer UI darzustellen (gut z. B. für web-basiertes UI-Design): Zustände = Bildschirmnamen, Aktivitäten/Aktionen = Aufzählungspunkte unter dem Bildschirmnamen (oft nur die Exit-Aktion gezeigt), Zustandsübergänge = Ergebnis der Exit-Aktion (Klick, Menüauswahl, Cursorbewegung).

Aktivitätsdiagramme (Übung 6-2)

Quelle: other/statecharts_activitydiagrams.pdf

  • Zerlegen eine Aktivität in kleinere Einheiten (Teil-Aktivitäten); jede Teil-Aktivität kann wiederum in einem eigenen Aktivitätsdiagramm weiter zerlegt werden.
  • Eine Aktivität hat (mindestens) einen Input und einen Output.

Kontrollflusssemantik (Tokens)

  • Der initiale Knoten erzeugt einen Token.
  • Eine Aktivität wird gestartet, sobald ihr Input einen Token erhält; nach Abschluss geht der Token an den Output, von dort dem Pfeil zum nächsten Knoten folgend.
  • Erst wenn alle Inputs eines Knotens einen Token haben, startet die Aktivität (implizites Join-Verhalten an einem einfachen Knoten mit mehreren eingehenden Pfeilen).

Aufteilung des Kontrollflusses

KonstruktBedeutung
Fallunterscheidung (branch/merge) — Rauteder Token verfolgt nur einen der Pfade (mit Guard-Bedingungen wie [alles verstanden])
Parallele Abarbeitung (fork/join) — Balkender Token wird vervielfacht, die Pfade werden nebenläufig beschritten und am Join wieder synchronisiert; ein einfacher Knoten mit mehreren ein-/ausgehenden Pfeilen wirkt implizit wie fork/join
  • Activity Final Node (gefüllter Kreis mit Ring): erreicht ein Token diesen Knoten, werden alle Tokens im Diagramm gelöscht — auch parallele Flüsse werden gestoppt.
  • Flow Final Node (Kreis mit X): löscht nur den ankommenden Token, hat keinen Einfluss auf evtl. parallele Flüsse.

Datenflüsse

  • Neben einfachen Kontroll-Tokens können auch komplexe Objekte von einer Aktivität zur nächsten geschickt werden — entweder über Pin-Notation (kleine Kästchen am Rand der Aktivität, benannt nach dem Objekttyp) oder über explizite Objekt-Knoten (eigene Kästchen zwischen den Aktivitäten).
  • Bedeutung: die Aktivität startet, sobald sie ein Objekt des erwarteten Typs erhält (auch das ist ein Token); nach Abschluss stellt sie einen Kontroll-Token und ggf. weitere Objekt-Tokens bereit, die unabhängig voneinander den Flüssen folgen.

Wann dominiert welches Modell?

Ein Modell heißt dominant, wenn es einen viel größeren Anteil der interessanten Information enthält als die anderen.
  • Einfaches Datenbanksystem: Operationen simpel (Laden, Speichern), aber komplexe Datenstrukturen → das statische Objektmodell dominiert.
  • Telefonvermittlungssystem: Datenstrukturen sagen wenig aus, Verhalten zu komplex für Use Cases → das dynamische Modell (insbesondere Statecharts) dominiert.

Anforderungsdokument (Requirements Document)

deckt sich mit uebersicht.txt Zeile 279-280: "enthält weit mehr als funktionale Anforderungen als Anwendungsfälle"

Wichtig: das Anforderungsdokument ist nur konzeptuell ein einzelnes Dokument — in der Praxis oft mehrere separate Dokumente, manche davon gar nicht schriftlich fixiert.

Mögliche Gliederung

  1. Introduction
  2. Current system
  3. Proposed system
    1. Overview
    2. Functional requirements
    3. Nonfunctional requirements
    4. Constraints ("Pseudo requirements")
    5. Analysis Model: 3.5.1 Scenarios (as-is/visionary), 3.5.2 Use Case Model, 3.5.3 Object Model (Data Dictionary + Klassendiagramme — das ist immer noch Analyse, kein Entwurf!), 3.5.4 Dynamic Model (Zustandsdiagramme für dynamisch wichtige Klassen, Sequenzdiagramme für kollaborierende Objekte), 3.5.5 User Interface (Navigationspfade, Screen-Mockups)
  4. Glossary

Kategorien nichtfunktionaler Anforderungen (3.3, mit Leitfragen)

User Interface & Human Factors, Documentation, Hardware Considerations, Performance Characteristics, Error Handling & Extreme Conditions, System Interfacing, Quality Issues, System Modifications, Physical Environment, Security Issues, Resources & Management Issues (Betrieb wird in diesem Kurs weitgehend ausgeklammert).

Priorisierung von Requirements

PrioritätMuss behandelt werden während
Hoch ("Core requirements")Analyse, Entwurf und Implementierung; muss bei Kundenabnahme erfolgreich demonstriert werden
Mittel ("Optional requirements")Analyse und Entwurf; oft erst in einer späteren Iteration implementiert/demonstriert
Niedrig ("Fancy requirements")nur Analyse ("sehr visionäre Szenarien"); zeigen mögliche künftige Nutzung, z. B. sobald neue Technik verfügbar wird

Konventionell vs. Agil

Ein detailliertes, formales Anforderungsdokument ist ein Kennzeichen konventioneller Projekte (oft Kern eines Festpreisvertrags) — trotz Umfang oft von zweifelhafter Qualität. Agile ("Lightweight") Prozesse vermeiden ein solches Dokument bewusst; ist ein "agiles Anforderungsdokument" weniger detailliert, kann seine Qualität trotzdem besser sein. Ein Blick auf die Anforderungsprozesse einer Organisation verrät viel über die Organisation selbst.
