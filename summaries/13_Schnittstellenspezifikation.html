Quelle: vl/13_Schnittstellenspezifikation.pdf + other/OCL.pdf — relevant für ub/09_ub_ocl.pdf

Einordnung: Objektentwurf (Object Design)

Aus der Anforderungsanalyse kommen Attribute/Operationen oft ohne Typinformation. Objektentwurf ergänzt das in vier Schritten (ein Detail-Teil der Modularisierung):

  1. Verbleibende Attribute/Operationen identifizieren
  2. Sichtbarkeit ergänzen (siehe 04 UML)
  3. Typsignaturen ergänzen (Parameter- und Rückgabetypen)
  4. Verträge (Contracts) ergänzen — dafür dient OCL

Contracts: Vor-/Nachbedingung, Invariante (Übung 9-1c/d)

Ausführliche Definition der drei Vertragsteile siehe 09 Architektur (Design by Contract)

Zusammenhang der Begriffe (Übung 9-1d): Design by Contract ist das Prinzip, für jede Klasse/Operation einen Vertrag festzulegen. Ein Vertrag besteht aus Constraints (booleschen Ausdrücken über Modellelemente): Preconditions (was der Aufrufer garantieren muss), Postconditions (was die Operation garantiert) und Invarianten (was für jedes Objekt der Klasse zu jedem Zeitpunkt gilt, außer während der Ausführung einer Operation — die Invariante ist implizit Teil jeder öffentlichen Postcondition). OCL (Object Constraint Language) ist die Sprache, in der diese Constraints formal aufgeschrieben werden — Teil der UML-Welt, aber syntaktisch von UML selbst getrennt und deklarativ (kein Kontrollfluss ausdrückbar).

OCL-Grundsyntax (Übung 9-2, 9-3)

Invarianten (Klassen-Constraints)

context <Klasse> inv: <Bedingung>

Gilt für alle Membervariablen/Exemplare der Klasse zu jeder Zeit (außer während einer Methodenausführung). self bezeichnet das jeweilige Exemplar; bei eindeutigem Kontext kann self weggelassen werden.

Vor-/Nachbedingungen (Operations-Constraints)

context <Klasse>::<Operation>(<Parameter>: <Typ>): <ReturnTyp>
  pre: <Bedingung 1>
  pre: <Bedingung 2>
  post: <Bedingung 3>

@pre greift innerhalb einer post-Bedingung auf den Wert eines Ausdrucks vor dem Aufruf zu, z. B. getNumPlayers() = getNumPlayers@pre() + 1. Achtung: OCL-Verträge machen implizit die Annahme "alles andere bleibt gleich" — das muss man ggf. explizit mit angeben, sonst ist der Vertrag unvollständig (z. B. zugelassen = zugelassen@pre).

result-Schlüsselwort: in der Postcondition einer Operation mit Rückgabewert bezeichnet result den zurückgegebenen Wert, z. B. context Klausur::punkteanzahl() post: result = aufgaben.punktzahl->sum().

Logische und relationale Operatoren

  • Logisch: and, or, xor, implies, not. implies: gilt die Bedingung davor, muss auch die danach gelten (sonst ist der Ausdruck automatisch wahr).
  • Relational: =, >, <, >=, <=, <>; Standard-Rechenoperatoren +, -, *, /.

Navigation durch das Klassendiagramm

Jeder OCL-Ausdruck lässt sich aus drei Navigationsarten zusammensetzen:

ArtBeispiel
Lokales Attributcontext Tournament inv: end - start <= Calendar.WEEK
Direkt verbundene Klassecontext Tournament::acceptPlayer(p) pre: league.players->includes(p)
Indirekt verbundene Klasse (über mehrere Assoziationen)context League::getActivePlayers() post: result = tournaments->iterate(t, p={} | p.union(t.players))

Objekt- vs. Collection-Navigation: Zugriff auf ein einzelnes Objekt mit . (Punkt), Zugriff auf Operationen einer Collection (wenn über eine "viele"-Assoziation navigiert wird) mit -> (Pfeil). Bei Assoziationsenden mit Maximum 1 liefert die Navigation immer ein einzelnes Objekt (oder null); trotzdem sind Collection-Operationen wie ->notEmpty() darauf anwendbar, weil implizit ein leeres bzw. einelementiges Set erzeugt wird.

Collections

Die meisten Assoziationen führen zu Collections (0..*-Multiplizität). OCL kennt vier Collection-Arten:

ArtEigenschaftBeispiel
Setkeine Duplikate, unsortiertSet{2,5,1,88}
OrderedSetkeine Duplikate, sortiertOrderedSet{1,2,5,88}
BagDuplikate erlaubt, unsortiertBag{1,3,4,3,5}
SequenceDuplikate erlaubt, sortiertSequence{1,2,3,3,45}

Welche Art konkret entsteht, hängt von den UML-Eigenschaften des Assoziationsendes ab ({unique}, {ordered}, …).

Wichtige Collection-Operationen

  • size() — Anzahl Elemente
  • includes(x) — enthält x?
  • select(expr) — filtert Elemente, für die expr wahr ist
  • union(coll) / intersection(coll) — Vereinigung / Schnittmenge
  • asSet() — konvertiert in eine (unsortierte, duplikatfreie) Menge
  • iterate(v, acc = init | expr) — allgemeinste Iteration mit Akkumulator (z. B. für Vereinigungen über mehrere Objekte)

Quantoren

  • forAll(v | expr): wahr, wenn expr für alle Elemente der Collection gilt.
  • exists(v | expr): wahr, wenn expr für mindestens ein Element gilt.
context Tournament inv:
  matches->forAll(m | m.start.after(self.start) and m.end.before(self.end))

allInstances()

Klasse.allInstances() liefert die Menge aller Exemplare einer Klasse — z. B. für "keine zwei Studierenden teilen sich eine Matrikelnummer":

context Student inv:
  Student.allInstances()->forAll(s | s <> self implies s.matrikel <> self.matrikel)

Nicht unnötig verwenden: Bedingungen, die nur self selbst betreffen (z. B. "Matrikelnummer ist mindestens 6-stellig": context Student inv: matrikelnummer >= 100000), brauchen kein allInstances() — das wäre unnötig aufwendig und verschleiert die eigentliche Aussage.

OCL in der Praxis

  • Faustregel: Preconditions und Invarianten lassen sich meist leicht ausdrücken; Postconditions sind oft schwierig — eine unvollständige Postcondition (mit erklärendem Kommentar für den Rest) ist meist besser als keine.
  • Zur Vereinfachung lohnt es sich, Prädikat-Methoden in der Klasse einzuführen (z. B. isPlayerAccepted(p) statt den Ausdruck jedes Mal auszuschreiben).
  • Werkzeugunterstützung: OCL kann zur Laufzeit-Codegenerierung genutzt werden (Quantoren oft nicht praktikabel umsetzbar); ähnliche Mechanismen existieren nativ in manchen Sprachen — Eiffel (require, ensure, invariant), Java (assert) oder per Preprocessor (z. B. JContract, Verträge als Javadoc-Tags @pre/@post/@invariant).
