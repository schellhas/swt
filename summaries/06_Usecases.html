06 Anwendungsfälle (Use Cases)

Quelle: vl/06_Usecases.pdf — relevant für ub/05_ub_use-cases.pdf und fabiuebersicht.txt (Zeilen 98-115, "Anwendungsfall")

Was ist ein Use Case?

Rolle: Vereinbarung zwischen den Beteiligten eines Projekts über das Verhalten des Systems.
Ansatz: Beschreibung des Verhaltens des Systems als Antwort auf einen Auftrag eines Hauptakteurs, der mit seinem Auftrag ein Ziel verfolgt und erreicht.
  • Ein Use Case bündelt die Beschreibungen für viele einzelne Fälle (Szenarios), die den Zielen nach eng zusammengehören — er ist also abstrakt, aber nicht sehr.
  • Form: normalerweise (meist strukturierter) Text; formale/grafische Notationen (Flussdiagramme, Zustandsdiagramme, Sequenzdiagramme, Petrinetze) sind zwar prinzipiell möglich, Text ist aber meist die beste Wahl. "Wer nicht gut Text schreiben kann, kann auch nicht gut Use Cases schreiben."

a) Was ist ein Anwendungsfall und wozu dient er? (Übung 5-1a)

Siehe Definition oben. Zweck: er dient als Vereinbarung zwischen allen Projektbeteiligten (Kunden, Nutzer·innen, Entwickler·innen) darüber, was das System in einer bestimmten Interaktion leisten soll — unabhängig von der konkreten Implementierung. Er macht funktionale Anforderungen konkret nachvollziehbar und dient zugleich als Werkzeug der Anforderungserhebung (leicht zu schreiben, leicht mit Beteiligten abzugleichen).

Akteure und Rollen

  • Akteure werden immer aus einer zum Use Case gehörenden Perspektive bezeichnet (z. B. "Käufer", "Geschädigter") — jede Bezeichnung führt also eine Rolle ein.
  • Im Anforderungsdokument muss zusätzlich festgelegt werden, welche Beteiligten welche Rollen unter welchen Umständen einnehmen können — das definiert Rechte, Benutzergruppen, GUI-Funktionsbündelung.

Wenn nicht klar ist, von welchem System (ganze Firma? zu bauendes System? Teilsystem?) die Rede ist, wird der Use Case unverständlich. Ein gutes Projekt hat meist: 1 Überblicks-Use-Case fürs ganze Projekt, ~1-4 Überblicks-Use-Cases je Zielbereich, je 1 Benutzerziel-Use-Case pro "in einer Sitzung" erledigtem Ablauf, und Detail-Use-Cases nur für besonders komplizierte, oft wiederverwendete Teilabläufe.

Konventionell vs. Agil

Konventionell: Überblicks-, normale und (selten) Whitebox-/Detail-Use-Cases werden meist ausformuliert. Agil: eher Epics und Story Cards ("Als <Rolle> kann ich <Ziel> von <SuD>, um <Akteursinteresse>") statt vollständiger Use Cases; Details werden eher im Code oder iterativ nachgebessert.

Präzision beim Schreiben von Use Cases

  • Präzision (precision) ≠ Richtigkeit (accuracy) — ein Use Case kann sehr präzise, aber falsch sein, oder ungenau, aber völlig richtig. Ziel: ausreichend präzise und richtig.
  • Gefahr 1 (zu früh zu genau): man übersieht anfangs oft etwas Wichtiges oder sitzt einem Missverständnis auf — schon investierte Detailarbeit ist dann verschwendet.
  • Gefahr 2: wird das Dokument zu umfangreich, liest es niemand mehr. Also: weniger ist oft mehr, Use Cases sollten immer nur gerade genau genug sein.

Empfehlung: schrittweise präziser machen

  1. Hauptakteur und Ziel ("Story Card") — klärt schon wichtige Anforderungen/Beteiligte, erst mal prüfen ob alles stimmt
  2. Haupt-Erfolgsszenario — reicht in manchen Fällen schon aus
  3. Erweiterungsbedingungen (welche Varianten/Fehler müssen behandelt werden?)
  4. Erweiterungsschritte (wie werden sie behandelt? — kann oft weggelassen und informell geklärt werden)

Wichtigkeit von Zielen

  • Ein Ziel beantwortet zu den Schritten die Frage "Warum?"; der Name eines Use Case sollte immer ein Ziel bezeichnen.
  • In einem umfassenderen Use Case tritt ein untergeordnetes Ziel als einzelner Schritt auf → es entsteht eine Zielhierarchie (hierarchische Zerlegung), die einzelne Use Cases übersichtlich hält.
  • Klare Akteursbenennung deckt oft Probleme auf (z. B. wenn "Arzt" eigentlich eine Organisation statt einer Person ist).

Szenario vs. Anwendungsfall (Übung 5-1c)

Ein Szenario ist eine konkrete(re) Ausprägung eines Use Case: es gibt keine Varianten, sondern nur einen linearen Ablauf, ggf. mit ganz konkreten Datenwerten.
Ein Use Case ist die abstraktere, allgemeinere Beschreibung, die mehrere Szenarien (Haupt-Erfolgsszenario + Erweiterungen/Varianten) bündelt.

Szenarien werden ergänzend genutzt, wenn das Schreiben eines Use Case schwerfällt oder er für manche Beteiligte zu abstrakt ist (meistens kommt man aber ohne aus). Der Entwicklungsstil ATDD (Acceptance-Test-Driven Development) nutzt statt eines Use Case direkt N konkrete Szenarien als automatisierte Testfälle, die vor der Implementierung geschrieben werden und selbst als Spezifikation dienen.

Checkliste für Use-Case-Bestandteile

Bei einem guten Use Case sollte jede dieser Fragen mit "ja" beantwortet werden können:

  • Titel: aktive Verbalphrase, die das Ziel des Hauptakteurs nennt? Ist das SuD für die Zielerreichung zuständig?
  • Bereich (SuD): angegeben? bei Systementwurf: alle Teile entworfen, nichts außerhalb der Systemgrenze?
  • Detailgrad/Zielniveau: liegt das Ziel wirklich auf diesem Niveau? passt der Inhalt zum geplanten Detailgrad?
  • Hauptakteur: hat er/sie/es Verhalten und ein zu einer Dienstzusicherung des SuD passendes Ziel?
  • Voraussetzungen: verbindlich und herstellbar? werden im Use Case selbst nicht mehr überprüft?
  • Beteiligte/Interessen, Mindestzusicherung, Zusicherung im Erfolgsfall: jeweils angemessen berücksichtigt/geschützt/befriedigt?
  • Haupt-Erfolgsszenario: 3-9 Schritte? beschreibt es den Ablauf vom Auslöser bis zur Erfolgsgarantie?
  • Jeder Einzelschritt: als erreichtes Ziel formuliert (z. B. "validieren" statt "prüfen")? treibt er den Prozess sichtbar voran? ist Akteur und Absicht klar? abstrahiert er von der Bedienoberfläche?
  • Erweiterungsbedingungen: kann/muss das SuD den Fall erkennen bzw. behandeln?
  • Insgesamt: "Ist dies, was Du möchtest?" (ggü. Beteiligten) und "Kannst Du das bauen?" (ggü. Entwickler·innen)

Grenzen von Use Cases

Use Cases decken nur Verhaltensanforderungen ab. Sie beschreiben nicht: Domäneneigenschaften/Annahmen, Geschäftsregeln, nichtfunktionale Anforderungen, ggf. vorgegebenes Datenmodell/technische Schnittstellen, sonstige Randbedingungen. Das Anforderungsdokument muss daher mehr als nur Use Cases enthalten — Use Cases bilden aber einen guten Rahmen für den Rest.

Aus Entwicklersicht fehlt zudem: welche Funktionen die SW braucht, welche Daten im System vorhanden sind, wie sich die Entwicklung auf Personen verteilen lässt — dafür ist als nächster Schritt Anforderungsanalyse nötig.

UML-Anwendungsfalldiagramme (Übung 5-2)

a) Anwendungsfalldiagramm vs. Anwendungsfall, Vor-/Nachteile
Ein Anwendungsfalldiagramm ist eine grafische Übersicht über Akteure und die wenigen Beziehungen zwischen Use Cases (Systemgrenze, include/extend/Generalisierung) — es enthält bewusst wenig Information und ersetzt nicht den ausformulierten (meist textuellen) Use Case selbst.
Vorteile: schneller visueller Überblick über Akteure und Struktur eines Systems; gut zur Kommunikation der Systemgrenze und Zusammenhänge zwischen Use Cases.
Nachteile: enthält keinerlei Verhaltens-/Ablaufdetails (kein Ersatz für den Text); kann leicht mit dem eigentlichen Use Case verwechselt werden ("bitte nie das Diagramm mit dem Use Case verwechseln!").
b) Akteur
Repräsentiert eine Rolle, die von außerhalb des Systems mit ihm interagiert (Person oder anderes System) — nicht eine konkrete Person, sondern die Perspektive/Funktion, aus der heraus agiert wird.
c) Weitere Modellelemente (drei Beispiele)
  • Subject/Systemgrenze (Rechteck, "system under discussion"): grenzt das betrachtete System von seiner Umgebung ab.
  • Use Case selbst (Oval): ein benannter Anwendungsfall innerhalb der Systemgrenze.
  • «include»-Beziehung (gestrichelter Pfeil): der ausführende Use Case ruft immer einen anderen Use Case auf — entspricht dem Unterstreichen von Schritten in der Textform.
d) Arten von Beziehungen zwischen zwei Use Cases
BeziehungBedeutungEntspricht in Textform
«include»zwingender Aufruf eines anderen (Unter-)Use Case als Teil des Ablaufsunterstrichener Schritt mit Verweis auf Unter-Use-Case
«extends» / Generalisierungoptionale/alternative, ausgelagerte Varianten und Fehlerfälle"extends"-Beziehung (Erweiterungen) bzw. "generalizes"-Beziehung (Alternativen/Fehlerfälle)
Beide dienen dazu, Use Cases übersichtlich zu halten, indem Teilabläufe ausgelagert werden — «include» ist dabei verpflichtend, «extends»/Generalisierung optional bzw. alternativ.

Präzisierung: include, extend, Generalisierung

ergänzt aus other/04_anwendungsfaelle.pdf (Lehrbuchkapitel "Anwendungsfalldiagramm", Beispiel "Bestellwesen") — deckt sich mit VL06, ist aber präziser in Pfeilrichtung und Semantik

  • include: Basisanwendungsfall A nutzt Anwendungsfall B (»A includes B«) — A ist vom erfolgreichen Ablauf von B abhängig. Der Pfeil zeigt vom benutzenden zum benutzten Use Case (A --«include»--> B), da A "Kenntnis" von B hat. Zweck: Redundanzvermeidung — dieselbe Teilfunktionalität wird nur einmal beschrieben. Die include-Beziehung sagt nichts über den Zeitpunkt aus, zu dem B im Ablauf von A passiert (Anfang, Ende, mittendrin) — sie wird immer erreicht.
  • extend: Anwendungsfall B erweitert A optional (»B extends A«) an einem benannten Erweiterungspunkt (extension point) in A, unter einer angegebenen Bedingung. Der Pfeil zeigt vom erweiternden zum Basis-Use-Case (B --«extend»--> A) — also genau entgegengesetzt zur include-Richtung. Zweck: Flexibilität/Erweiterbarkeit des Anwendungsfallmodells; die zusätzliche Funktionalität ist optional, A liefert auch ohne sie ein sinnvolles Ergebnis. In der UML bleibt die genaue Semantik unklar/kompliziert — extend wird oft einfach als include mit Bedingung interpretiert.
  • Generalisierung zwischen Use Cases: analog zur Klassengeneralisierung (Pfeil mit geschlossener, nicht gefüllter Spitze vom spezielleren zum allgemeineren Use Case). Der speziellere Use Case (z. B. "Mahnung erstellen") übernimmt die Aufgabe des allgemeineren ("Forderung stellen"), erledigt aber Teilaufgaben auf spezielle Art. Beziehungen des allgemeineren Use Case zu Akteuren werden dabei mitvererbt.
  • Wichtig: zyklische Abhängigkeiten (ein Use Case nutzt/erweitert sich selbst, direkt oder über mehrere Stufen) müssen vermieden werden.

Textuelles Schema (alternative, einfachere Notation)

Neben der ausführlichen Cockburn-Schablone oben gibt es ein einfacheres, verbreitetes Schema: use case Name / actors ... / precondition ... / main flow ... / alternative flow X ... / postcondition ... / exceptional flow Y ... / postcondition ... / end Name. Ein Szenario ist hier explizit als "Instanziierung" eines Use Case auf einen konkreten Fall definiert. Akteur-Generalisierung ist ebenfalls möglich: ein spezielleres Akteur (z. B. "Privatkunden-Sachbearbeiter") kann mindestens die Rolle des allgemeineren Akteurs ("Sachbearbeiter") spielen — nützlich zur Redundanzvermeidung bei gemeinsamen Verantwortlichkeiten mehrerer Akteure.
