    05 W6H-Technik

    Requirements Elicitation

    • Ausgangspunkt: die Vorstellung, dass es ein zu lösendes "Problem" gibt (etwas Negatives, das beseitigt werden soll, oder eine Chance, die genutzt werden soll).
    • W6H-Technik (die Journalisten-Technik) zum Identifizieren von Problem und Chance:
    Frageliefert
    Which problem needs solving?Problem-Boundaries
    Where is the problem?Context/Problem Domain
    Whose problem is it?Stakeholders (Betroffene, Beteiligte)
    Why does it need solving?Stakeholder-Goals
    How might a SW system help?Scenarios
    When and how does it need solving?Development Constraints
    What might prevent solving it?Feasibility und Risk

    Schwierigkeiten der Erhebung

    • Eingeschränkte Beobachtbarkeit: Problem-Owner oft zu beschäftigt mit dem Problem selbst; Anwesenheit eines Beobachters kann das Problem verändern.
    • Dünn verteiltes Domänenwissen: über viele Quellen verteilt, selten explizit verfügbar.
    • Bias: Leute dürfen/wollen manchmal nicht sagen, was man wissen muss (politisches Klima, versteckte Agenden).
    • Konflikte zwischen Quellen (unterschiedliche Ziele oder Verständnisse).
    • Tacit Knowledge ("say-do"-Problem): Expert·innen kennen ihr eigenes Wissen nicht bewusst — können Einzelfälle lösen, aber keine allgemeine Regel nennen; dazu Repräsentationsprobleme (fehlende Sprache, ungenaue gesprochene Sprache) und Brittleness (Wissen wird beim Erheben erst erzeugt, nicht extrahiert — unvollständig, zu stark vereinfacht).
    • Distortions: senderseitig (Group Think, Impression Management, Verfügbarkeitsheuristik, Unterschätzung von Unsicherheit), empfängerseitig (Fehlinterpretation, Fehlrepräsentation, Anchoring), beidseitig (Inkonsistenz).
    • Persönliche/zwischenmenschliche Faktoren.
    05 Was ist ein System?

    Was ist ein System?

    • Ein Teil der Realität, der beobachtbar mit seiner Umgebung interagiert; durch eine Boundary (Grenze) abgetrennt (kann bei "soft systems" schwer zu bestimmen sein), erhält Inputs, sendet Outputs, hat oft einen Kontrollmechanismus und meist interessante emergente Eigenschaften.
    • Die zu bauende Software ist im Lösungsraum "das System" — im Problemraum nicht: dort gehören auch die Menschen, ihre Nutzungsweisen und weitere Umweltfaktoren zum größeren, zu verstehenden System → sozio-technisches System.
    • Faustregel: Sind Menschen irgendwie beteiligt, Software niemals mit "dem System" verwechseln.

    Application Domain vs. Solution Domain (Übung 6-1a)

    Application Domain (Problembereich)Solution Domain (Lösungsbereich)
    Was ist das?die "Heimat"-Domäne des zu lösenden Problemstechnische Domänen, die beim Bau der Software helfen
    BeispieldomänenFinanzwesen, Meteorologie, GesundheitswesenTelekommunikation, Datenbanken, Compilerbau, Betriebssysteme, Web-Technologie
    Problembereichsklasse (application/problem domain class)eine Abstraktion in der Anwendungsdomäne (in Business-Anwendungen oft "Business Object" genannt); kommt in Analyse- und Entwurfsmodell vor—
    Lösungsklasse (solution domain class)—eine Abstraktion, die aus technischen Gründen eingeführt wird, nicht direkt wegen der Anwendungsanforderungen; kommt nur im Entwurfsmodell vor
    BeispieleContract, AirPressure, PrescriptionBuffer, DatabaseConnection, Parser, Filehandle, Tag

    Wichtig: Das Analysemodell (Objektmodellierung dieser Vorlesung) beschreibt ausschließlich Problembereichsklassen — es ist explizit kein Lösungsentwurf ("It is not meant to be a solution design!").

    07 Abbott-Textanalyse

    Wie findet man Klassen? Abbotts Textanalyse

    Methoden (mehrere kombinieren): Kunden beobachten/befragen, Weltwissen & Intuition nutzen, syntaktische Analyse von Anforderungstexten/Szenarien (Abbott 1983, "noun-verb analysis").

    BeispielGrammatikalische Konstruktionmögliche UML-Komponente
    "Monopoly"konkrete Person/SacheObject
    "toy"NomenClass
    "3 years old"AdjektivAttribute
    "enters"VerbOperation
    "depends on…"intransitives VerbOperation (Event)
    "is a", "either…or", "kind of…"klassifizierendes VerbInheritance
    "has a", "consists of"possessives VerbAggregation
    "must be", "less than…"ModalverbConstraint

    Ablauf des Object Modeling

    1. Szenarien formulieren (mit Endnutzer/Domänenexpert·in)
    2. Use Cases aus den Szenarien extrahieren
    3. Flow of Events analysieren (z. B. mit Abbotts Textanalyse)
    4. Klassendiagramm erzeugen: Klassen → Attribute/Operationen → Assoziationen → Multiplizitäten → Rollen

    Reihenfolge ist nur eine Heuristik, flexibel; Iteration hilft. Werden falsche Abstraktionen gefunden, müssen Inkonsistenzen erkannt und das Modell korrigiert werden.

    05 D/R/S, S+D⟹R

    Requirements, Domain Properties und Spezifikation

    • Domain Properties (D): Eigenschaften im Problemraum, die wahr sind — unabhängig davon, ob das System je gebaut wird.
    • Requirements (R): Eigenschaften im Problemraum, die durch das gelieferte System wahr gemacht werden sollen.
    • Spezifikation (S): Beschreibung des Verhaltens des Programms im Lösungsraum, das nötig ist, um R zu erfüllen.
    • Zusammenhang: S + D ⟹ R (die Spezifikation erfüllt zusammen mit den Domain Properties die Requirements). Ist das Domänenmodell falsch, kann diese Schlussfolgerung trotz korrekter Spezifikation scheitern — ein·e umsichtige·r Softwareentwickler·in hinterfragt daher alle Domänen-Annahmen.

    Validierung vs. Verifizierung

    deckt sich mit uebersicht.txt Zeilen 25-29

    Verifizierung (Verification): prüft, ob das Programm auf einem bestimmten Computer die Spezifikation erfüllt (Äquivalenz formaler Repräsentationen).
    Validierung (Validation): umfassender — prüft, ob das System die tatsächlichen Erwartungen in der realen Welt erfüllt; das schließt implizit ein: Haben wir alle wichtigen Requirements verstanden? Haben wir alle relevanten Domain Properties verstanden?

    Validierungskriterien für Requirements: Correctness (entsprechen der Sicht des Kunden), Completeness (alle Szenarien inkl. Ausnahmefällen beschrieben), Consistency (keine Widersprüche zwischen Requirements), Ambiguity/Unambiguousness (nicht vage — alle plausiblen Interpretationen sind akzeptable Lösungen), Feasibility/Realism (realistisch umsetzbar), Traceability (jede Systemfunktion lässt sich auf ein Requirement zurückführen — erst bei Auslieferung).

    ergänzt aus vl/08_Dynamische-Modellierung.pdf

    • Verifikation ist ein Äquivalenz-Check zwischen zwei verwandten Modellen: das zweite wurde per Transformation aus dem ersten abgeleitet (Analyse → System-Entwurf → Objekt-Entwurf → Implementierung) — war die Transformation korrekt?
    • Validierung ist anders: es gibt kein zweites Modell, man vergleicht ein Modell direkt mit der Realität R (kann auch ein künstliches System wie ein Altsystem sein) — das betrifft nur den allerersten Schritt (R → MAnalysis) sowie den finalen Abnahmetest.
    • Techniken für Requirements-Validierung: formale/informelle Reviews (Meetings, Requirements Review); für Implementierungen: Abnahmetest, System Use.

    What vs. How

    • "Requirements should specify what without specifying how" — aber die Grenze ist nicht immer eindeutig: das "Wie" einer Abstraktionsebene ist das "Was" der nächsttieferen (System → Subsystem → Unit).
    • What: bezieht sich auf den Zweck des Systems, extern, Eigenschaft der Anwendungsdomäne.
    • How: bezieht sich auf Struktur/Verhalten des Systems, intern, Eigenschaft der Lösungsdomäne.
    • Schnittstellen (Interfaces) sind die Grenze zwischen "What" und "How".
    • Anwendungsdomäne vs. Technische Domäne (uebersicht.txt Zeilen 183-189): Anwendungsdomäne = Problembereich, wozu die Software dient (z. B. Finanzwesen, E-Commerce, Bildung — entspricht "What"); Technische Domäne = Lösungsbereich, mit welcher Technik sie realisiert wird (z. B. Java, NoSQL, Angular — entspricht "How"). Feinere Unterscheidung auf Klassenebene (Problembereichs-/Lösungsklassen) siehe 07 Objektmodellierung.

    06 Was ist ein Use Case?

    Was ist ein Use Case?

    Rolle: Vereinbarung zwischen den Beteiligten eines Projekts über das Verhalten des Systems.
    Ansatz: Beschreibung des Verhaltens des Systems als Antwort auf einen Auftrag eines Hauptakteurs, der mit seinem Auftrag ein Ziel verfolgt und erreicht.
    • Ein Use Case bündelt die Beschreibungen für viele einzelne Fälle (Szenarios), die den Zielen nach eng zusammengehören — er ist also abstrakt, aber nicht sehr.
    • Form: normalerweise (meist strukturierter) Text; formale/grafische Notationen (Flussdiagramme, Zustandsdiagramme, Sequenzdiagramme, Petrinetze) sind zwar prinzipiell möglich, Text ist aber meist die beste Wahl. "Wer nicht gut Text schreiben kann, kann auch nicht gut Use Cases schreiben."

    a) Was ist ein Anwendungsfall und wozu dient er? (Übung 5-1a)

    Siehe Definition oben. Zweck: er dient als Vereinbarung zwischen allen Projektbeteiligten (Kunden, Nutzer·innen, Entwickler·innen) darüber, was das System in einer bestimmten Interaktion leisten soll — unabhängig von der konkreten Implementierung. Er macht funktionale Anforderungen konkret nachvollziehbar und dient zugleich als Werkzeug der Anforderungserhebung (leicht zu schreiben, leicht mit Beteiligten abzugleichen).

    06 Checkliste (Titel, Einzelschritt)

    Checkliste für Use-Case-Bestandteile

    Bei einem guten Use Case sollte jede dieser Fragen mit "ja" beantwortet werden können:

    • Titel: aktive Verbalphrase, die das Ziel des Hauptakteurs nennt? Ist das SuD für die Zielerreichung zuständig?
    • Bereich (SuD): angegeben? bei Systementwurf: alle Teile entworfen, nichts außerhalb der Systemgrenze?
    • Detailgrad/Zielniveau: liegt das Ziel wirklich auf diesem Niveau? passt der Inhalt zum geplanten Detailgrad?
    • Hauptakteur: hat er/sie/es Verhalten und ein zu einer Dienstzusicherung des SuD passendes Ziel?
    • Voraussetzungen: verbindlich und herstellbar? werden im Use Case selbst nicht mehr überprüft?
    • Beteiligte/Interessen, Mindestzusicherung, Zusicherung im Erfolgsfall: jeweils angemessen berücksichtigt/geschützt/befriedigt?
    • Haupt-Erfolgsszenario: 3-9 Schritte? beschreibt es den Ablauf vom Auslöser bis zur Erfolgsgarantie?
    • Jeder Einzelschritt: als erreichtes Ziel formuliert (z. B. "validieren" statt "prüfen")? treibt er den Prozess sichtbar voran? ist Akteur und Absicht klar? abstrahiert er von der Bedienoberfläche?
    • Erweiterungsbedingungen: kann/muss das SuD den Fall erkennen bzw. behandeln?
    • Insgesamt: "Ist dies, was Du möchtest?" (ggü. Beteiligten) und "Kannst Du das bauen?" (ggü. Entwickler·innen)
    06 Wichtigkeit von Zielen

    Wichtigkeit von Zielen

    • Ein Ziel beantwortet zu den Schritten die Frage "Warum?"; der Name eines Use Case sollte immer ein Ziel bezeichnen.
    • In einem umfassenderen Use Case tritt ein untergeordnetes Ziel als einzelner Schritt auf → es entsteht eine Zielhierarchie (hierarchische Zerlegung), die einzelne Use Cases übersichtlich hält.
    • Klare Akteursbenennung deckt oft Probleme auf (z. B. wenn "Arzt" eigentlich eine Organisation statt einer Person ist).

    06 Checkliste (Erweiterungsbedingungen)

    Checkliste für Use-Case-Bestandteile

    Bei einem guten Use Case sollte jede dieser Fragen mit "ja" beantwortet werden können:

    • Titel: aktive Verbalphrase, die das Ziel des Hauptakteurs nennt? Ist das SuD für die Zielerreichung zuständig?
    • Bereich (SuD): angegeben? bei Systementwurf: alle Teile entworfen, nichts außerhalb der Systemgrenze?
    • Detailgrad/Zielniveau: liegt das Ziel wirklich auf diesem Niveau? passt der Inhalt zum geplanten Detailgrad?
    • Hauptakteur: hat er/sie/es Verhalten und ein zu einer Dienstzusicherung des SuD passendes Ziel?
    • Voraussetzungen: verbindlich und herstellbar? werden im Use Case selbst nicht mehr überprüft?
    • Beteiligte/Interessen, Mindestzusicherung, Zusicherung im Erfolgsfall: jeweils angemessen berücksichtigt/geschützt/befriedigt?
    • Haupt-Erfolgsszenario: 3-9 Schritte? beschreibt es den Ablauf vom Auslöser bis zur Erfolgsgarantie?

    • Insgesamt: "Ist dies, was Du möchtest?" (ggü. Beteiligten) und "Kannst Du das bauen?" (ggü. Entwickler·innen)

    06 Präzision / Reihenfolge

    Präzision beim Schreiben von Use Cases

    • Präzision (precision) ≠ Richtigkeit (accuracy) — ein Use Case kann sehr präzise, aber falsch sein, oder ungenau, aber völlig richtig. Ziel: ausreichend präzise und richtig.
    • Gefahr 1 (zu früh zu genau): man übersieht anfangs oft etwas Wichtiges oder sitzt einem Missverständnis auf — schon investierte Detailarbeit ist dann verschwendet.
    • Gefahr 2: wird das Dokument zu umfangreich, liest es niemand mehr. Also: weniger ist oft mehr, Use Cases sollten immer nur gerade genau genug sein.

    Empfehlung: schrittweise präziser machen

    1. Hauptakteur und Ziel ("Story Card") — klärt schon wichtige Anforderungen/Beteiligte, erst mal prüfen ob alles stimmt
    2. Haupt-Erfolgsszenario — reicht in manchen Fällen schon aus
    3. Erweiterungsbedingungen (welche Varianten/Fehler müssen behandelt werden?)
    4. Erweiterungsschritte (wie werden sie behandelt? — kann oft weggelassen und informell geklärt werden)

    Wichtigkeit von Zielen

    • Ein Ziel beantwortet zu den Schritten die Frage "Warum?"; der Name eines Use Case sollte immer ein Ziel bezeichnen.
    • In einem umfassenderen Use Case tritt ein untergeordnetes Ziel als einzelner Schritt auf → es entsteht eine Zielhierarchie (hierarchische Zerlegung), die einzelne Use Cases übersichtlich hält.
    • Klare Akteursbenennung deckt oft Probleme auf (z. B. wenn "Arzt" eigentlich eine Organisation statt einer Person ist).

    06 Grenzen von Use Cases

    Grenzen von Use Cases

    Use Cases decken nur Verhaltensanforderungen ab. Sie beschreiben nicht: Domäneneigenschaften/Annahmen, Geschäftsregeln, nichtfunktionale Anforderungen, ggf. vorgegebenes Datenmodell/technische Schnittstellen, sonstige Randbedingungen. Das Anforderungsdokument muss daher mehr als nur Use Cases enthalten — Use Cases bilden aber einen guten Rahmen für den Rest.

    Aus Entwicklersicht fehlt zudem: welche Funktionen die SW braucht, welche Daten im System vorhanden sind, wie sich die Entwicklung auf Personen verteilen lässt — dafür ist als nächster Schritt Anforderungsanalyse nötig.
