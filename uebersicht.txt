Arten von Anforderungen
	Eigenschaften der Problemdomäne
	Funktionale Anforderungen
		- Was das System tut: Die interaktion zwischen dem System und der Umgebung, unabhängig von der Implementierung
	Nichtfunktionale Anforderungen
		- Beobachtbare Aspekte des Systems, welche nicht direkt funktional sind
	Sicherheitsanforderungen
		- Eine Art von nicht funktionaler Anforderungen: Verhalten, das das System niemals an den Tag legen darf
	Einschränkungen
		- Einschränkungen für das System, welche zu verwendende Technologie haben soll

Validierung
	Überprüft ob ein Produkt die tatsächlichen Anforderungen und Bedürfnisse des Endnutzers erfüllt -> Feedback Sessions

Verifizierung
	Überprüft, ob ein Produkt den spezifischen Anforderungen und Design-Vorgaben entspricht -> Code reviews/Unit-tests

Wie baut man eine SW?
	- Entscheiden wie/wo/wodurch die funktionalen Anforderungen umgesetzt werden können
	- Herausfinden, wie man dabei die nicht funktionalen Anforderungen alle erfüllt kann
	Prinzipien von Entwurf
		- Trennung von Belangen: Wir teilen Probleme, damit wir wissen können falls ein Problem eintritt wo wir das problem finden können, bzw. wo wir das lesen können
		- Architektur: Globale Struktur festlegen "Grobentwurf", insbesonders für das Erreichen der nichtfunktionalen Anforderungen
		- Modularisierung: Trennung von Belangen durch Modularisierung, Kombination der Teile durch Schnittstellen "Information hiding, Lokalität"
		- Wiederverwerndung: Erfinde Architekturen und Entwurfsmoster nicht immer wieder neu
		- Dokumentation: Halte sowohl Schnittstellen als auch zu Grunde liegende Entwurfsentscheidungen und deren Begründungen fest

Tests
	- Defekttest: Ziel ist Zuverlässigkeitsprüfung, Findung von Versagen
	- Testen: Anwenden eines Testfalls auf einen Testgegenstand
	- Testfall: ein Tupel (Systemzustand (Testeingabe), Eingaben (Testeingabe), Systemverhalten (Testausgabe)), das erwartete Verhalten beschreibt
	- Testgegenstand: System oder Teil davon, der (Komponente) getestet werden soll
	- Testdurchführung (Testausführung): Gibt ein Testergebnis -> evtl. Defekt aufdecken

Wer soll testen?
	- Entwickler des Codes: Schnelle rückmeldung, Effizienz -> kennt sein Code schon
		- Betriebsblindheit -> Dinge übersehen, Einseitige Perspektive
	- Jemand anders: Frische Augen, Code wird gründlich getestet, ohne Annahmen war rein/raus kommen soll. Wissenasutausch. Zeitaufwand, Kosten, Missverständnisse
	- Gut kann TDD sein, automatisierte Tests
		- mehr testen
		- tests wiederholen (falls sich etwas ändert)

Anwendungsfall
	Was ist ein Anwendungsfall? (Textform)
		- Vereinbarung zwischen den Beteiligten eines Projektes über das Verhalten des Systems
		- Beschreibt das Verhalten des Systems, wo der Hauptakteur ein Ziel verfolgt und erreicht
		- Ein Anwendungsfall gruppiert die Beschreibungen fpr viele einzelne Fälle "Szenarios", die den Zielen eng zusammen gehören
		- Beschreibt die Funktionalen Anforderungen
	Anwendungsfall (Template)
		- Hauptakteur: Primär Benutzer oder System
		- Anwendungsbereich: Kontext & Grenzen
		- Niveau: Detaillierungsgrad
		- Beteiligte und Interessen
		- Vorraussetzung: Bedienung vor Ausführung
		- Mindestzusicherung: Grundlegende Garantie bei Fehlschlag -> Protokollieren
		- Zusicherung im Erfolgsfall: Gewünschtes Ergebnis
		- Auslöser: Ereignis das den Use Case startet
		- Haupt-Erfolgsszenario: Schritt für Schritt Prozess zum Ziel
		- Erweiterungen: Alternative Wege und fehlerfälle

Wirkung von Modularisierung
	Schnittstellen verbergen (hide) die Entwurfsentscheidungen, die sich öfter mal ändern -> Schnittstelle merkt nichts: Nur Modul wird verändert. System ist dann einfach zu verstehen

Module beurteilen
	Wie man gute Modularisierung findet
	1. Ein Modul hat eine gut verständliche Zuverlässigkeit "Responsibility"
	2. Module sind nicht größer als nötig
	3. Module sind meistens viel komplexer als ihre Schnittstellen
	4. Ändere Entscheidungen sind verborgen "hidden, Information hiding"

Arten von Tests
	Testfälle finden: Bekannte Versagensfälle, Erfahrung
	Black Box Test -> Funktionstest
		- Wähle Testfälle durch betrachtung der Spezifikation (Schnittstelle) der Komponente/Module
		- Für jeden Fall mit andersartigen Verhalten wähle mindestens einen Testfall
		- Gruppe solcher Fälle in Äquivalenzklassen, Fehlerfälle, Randfälle
	White Box Test -> Strukturtest
		- Wähle Testfälle durch Betrachtung der Implementation (Struktur) der Komponente/Module
		- Ziel: Abdeckung aller Elemente der implementation durch die Summe der Testfälle
		- C0 Anweisungsüberdeckung
		- C1 Bedienungsüberdeckung
		- C2 Schleifenüberdeckung
		- Datenflusskriterien

Taxonomie: Die Welt der Softwaretechnik
	Welt der Problemstellung
		Produktprobleme (Komplexitätsprobleme)
			Emergente Eigenschaften:
				Phänomene die man nur versteht, wenn man alle Teile betrachtet
			Komplexität:
				Ein System besteht aus vielen Einzelnteilen und hat emergente Eigenschaften
			Anforderungsprobleme -> Problemraum
				-> herausfinden, was gebaut werden soll
			Entwurfsprobleme -> Lösungsraum
				-> herausfinden, wie die SW strukturiert werden sollte, um die Anforderungen gut zu erfüllen
		Prozessprobleme (Pysycho-soziale Probleme)
			Entstehen weil Menschen Schwächen haben und zur Konstruktion von SW müssen Menschen zusammenarbeiten
			Kognitive Beschränkung
				-> denkfähigkeit
			Mängel der Urteilskraft
				-> emergente Eigenschaften, keine komplett richtige Entscheidungen treffen
			Kommunikation, Koordination
				-> info weiterleiten
			Gruppendynamik
				-> kann dazu führen, dass keine kritische Fragen gestellt werden
			Verborgene Ziele
				-> Menschen haben eigene Ziele
			Fehler
				-> Fehler können Auftreten
	Welt der Lösungsansätze
		Technische Ansätze "hart"
			Konkrete technische Maßnahmen und Lösung, wie die Implementierung von Algorithmen
			Abstraktion
				-> Konzentration auf wesentliche Eigenschaften durch weglassen von Details
			Wiederverwendung
			Automatisierung
				-> übertrage eine wiederholt zu erledigende tätigkeit an den computer
		Methodische Ansätze "weich"
			Strukturelle und organisatorische Methoden, wie die Anwendung von agilen Entwicklungsprozessen
			Anforderungsermittlung
				-> systematisch festlegen
			Entwurf
				-> Es ist wichtig eine Struktur/Funktionsweise vorab für da System festzulegen
			Qualitätssicherung
				-> man macht oft Fehler die zu schweren Mängeln in der SW führen können (konstruktive/analytische)
			Projektmanagement
				-> Bau einer großeren SW verlangt nach Planung, Leitung, Koordination

Iterative Prozessmodelle
	gut für unklaren oder mit verständlichen Anforderungen umgehen -> Allgemeine Ziele anstatt konkrete Pläne -> Agile Methoden verlängern sehr enge Kommunikation
	Prototypmodell: Baue Anfangs ein (Teil)System "zum wegwerfen", um kritische Anforderungen besser zu verstehen. Danach folgt ein Prototyp oder Wasserfallmodell
	Inkrementelles Modell: Baue das Gesamtsystem schrittweise. In jedem Schritt werden nur neue Teile hinzugebaut, aber es wird (theoretisch) nie etwas existierendes verändert
	Iteratives Modell: Baue das Gesamtsystem schrittweise. In jedem Schritt werden neue Teile hinzugebaut und wo nötig auch existierende verändert
		- Scrum
			-> Springs. Product Owner, Scum Master, Development Team
			Daily Scrum: Kurze Meetings für fortschrittbesprechung
		- XP
			flexible und gute Anpassung. Pair Programming, TDD, Kunde vor Ort
	Spiralmodell: Risikomodell. Tue in jede Iteration das, was am stärksten zur verringerung des kritischen projektrisikos biträgt. das hat alle däge Modelle als Spezialfälle

Wiederverwendung
	bedeutet meistens auch Abstützen auf Erfahrungen und fördert somit meistens das normale Vorgehen
		Qualität und Produktivität gehen hoch, Risiko geht runter

Prinzipien zur Wiederverwendung
	- normales Vorgehen
	- Universalität -> fast alles lässt sich im Prinzip wiederverwenden
	- Abwägung (trade off)
		-> wäge sorgfältig den Gewinn an Produktivität und (hoffentlich) Qualität ab gegen den Verlust an Flexibilität und Kontrolle

Schwächen vom Wasserfallmodell
	-> unklare Anforderungen

Strikte, stark planende Modelle
	für
	-> wenn ein wohldefiniertes Resultat in definierter Zeit erreicht werden muss
	-> wenn sehr große (und verteilte) Projektgruppen koordiniert werden müssen
Agile Modelle
	für
	-> wenn hohe Unsicherheit über die Anforderungen besteht
	-> wenn Änderungen von außen häufig sind (Anforderungen, Budget, Zeitplan)
